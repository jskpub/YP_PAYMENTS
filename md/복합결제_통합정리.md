## 1. PRD — 복합결제 개요

### 1.1 정의

- 하나의 상품에 대해 **회사 지원금**과 **직원 결제금액**이 동시에 발생하며, 이 둘을 **하나의 Order ID**로 통합 관리하는 결제 방식.
- 추천도서: 회사 100% 지원 → 직원 결제 0원 (단일 결제 주체, 복합결제 아님)
- 개인도서: 회사 지원금 + 직원 카드 결제 → **복합결제 대상**

### 1.2 핵심 예시 (원문 그대로, §7)

```
도서금액             25,000원
B2B 기업 지원금       10,000원
직원 결제금액         15,000원
──────────────────────
최종 결제금액         15,000원 (직원 실결제)
```

> "시스템상으로는 회사 지원금 + 직원 결제금액을 하나의 주문번호로 관리한다." (원문)

### 1.3 지원금 계산 로직 (전제 조건 — 복합결제 금액을 결정하는 규칙)

> 참고: 지원금 계산 자체의 화면(도서상세 등)은 별도 작업자 담당 영역이며, 아래는 결제 화면에서 그대로 이어받아 사용하는 **계산 결과값의 근거**만 정리.

| 구분     | 회사 지원금                   | 직원 결제금           |
| -------- | ----------------------------- | --------------------- |
| 추천도서 | 판매금액 100%                 | 0원                   |
| 개인도서 | MIN(판매금액 × 50%, 10,000원) | 판매금액 − 회사지원금 |

개인도서 예시:
| 도서가격 | 회사지원 | 직원부담 |
|---|---|---|
| 10,000 | 5,000 | 5,000 |
| 16,000 | 8,000 | 8,000 |
| 20,000 | 10,000 | 10,000 |
| 30,000 | 10,000 | 20,000 |
| 40,000 | 10,000 | 30,000 |

월 1권 제한(추천/개인 각 1권), 매월 1일 자동 리셋, 미사용 이월 없음(통계만 기록) — Rule Engine 정책, 상세는 지원금 담당 문서 참고.

### 1.4 결제 프로세스 (원문 §7 순서 그대로)

```
상품 선택 → 지원금 자동 계산 → 회사 지원금 차감(DB) → 직원 부담금 계산
→ 직원 결제(PG) → 주문 완료(1개 Order ID) → 배송/전자책 제공 → 환불 처리
```

### 1.5 PG 연계 — 확정되지 않은 최우선 이슈

> "기존 영풍문고 PG 구조에서 지원 가능한지 확인 필요." (원문 §15③)
> 요구사항\_정리.pdf 회신: "영풍문고의 기존 PG사와 동일합니다." — **PG사는 확정**되었으나, **단일 주문에 2개 결제 주체(회사/직원)를 동시 처리하는 복합결제 기능 자체의 기술적 지원 여부는 별도 확인 필요** (PG사가 같다고 복합결제 기능이 보장되는 것은 아님).

처리 방식 옵션 (미확정, 택1 필요):
| 옵션 | 방식 |
|---|---|
| 1 | 직원 결제만 PG 사용 / 회사 지원금은 DB 차감만 (PG 미경유) |
| 2 | 회사 지원금도 PG를 통해 결제 (가상 결제수단 등) |
| 3 | PG가 복합결제 자체를 지원 시 동시 처리 |

**권장 구조** (PG 미확정 시 기본 설계):

```
상품 선택 → 지원금 계산 → 회사 지원금 차감(DB 처리)
→ 직원 결제 부담금 계산 → 직원 결제(PG 요청) → 주문 완료(1개 Order ID)
```

### 1.6 환불/취소 — 확정되지 않은 최우선 이슈

> "20,000원짜리 개인도서를 구매해서 B2B 기업 10,000원 / 직원 10,000원을 결제했는데 직원이 도서를 취소한다면? 회사 지원금 10,000원을 어떻게 회수할 것인지가 필요함." (원문 §8)

요구사항\_정리.pdf 회신: "우리가 구매하는 유통플랫폼에서 카드 및 리워드로 구매한 후 취소 환불하고 동일한 상황으로 인식하시면 됩니다." — 다만 이 답변이 Rule Engine 상의 **회사 지원금 환수 로직**(월 한도 복원 포함) 설계에 충분한지는 **별도 검토 필요**로 남아있음.

환불 시 처리 원칙 (설계 기준):

```
원 구매: 20,000원 (회사 10,000 + 직원 10,000)
환불 시:
- 회사 지원금 10,000원 복원 (월 한도 복원, 재신청 가능)
- 직원 결제금 10,000원 환불 (PG 환불)
- 동시 처리 (양쪽 금액 동시 복원) 필수
```

미확정 세부 정책 체크리스트:

- [ ] 부분 환불 지원 여부 (장바구니 내 일부 도서만 환불)
- [ ] 전자책 취소 가능 여부 및 지원금 복원 기준
- [ ] 환불 처리 기한
- [ ] 환불 수수료 정책
- [ ] 월 지원한도 복원 여부(=재신청 가능 여부)

### 1.7 데이터 구조

**Order 테이블** (복합결제 핵심 — 회사/직원 금액을 한 레코드에 함께 보유)

```
Order ID / Employee ID / Order Type(추천·개인) / Book ISBN / List Price / Selling Price
/ Company Subsidy / Employee Payment / Order Date
/ Order Status(주문중·대기·결제완료·배송중·완료·취소) / Format(종이·전자)
/ Refund Status(Y/N) / Review Status(Y/N)
```

**Payment 테이블** (복합결제이므로 하나의 Order에 결제 레코드가 2건 생성될 수 있음)

```
Payment ID / Order ID / Payment Type(회사 지원금 / 직원 결제)
/ Payment Amount / Payment Status(예약·승인·실패·환불) / Payment Date
/ Payment Gateway Response
```

**Subsidy_Transaction 테이블** (지원금 차감/복원 이력)

```
Transaction ID / Order ID / Employee ID / Book Type / Amount
/ Status(적용·취소·환불) / Transaction Date
```

### 2.1 화면 흐름 (복합결제 관점)

```

    ↓
마이페이지 > 지원금 현황 / 구매내역 / 환불·취소(복합결제 역방향 처리) ★
```

## 3. 페이지별 상세 설계 (★ 본 문서 담당 범위)

### Page 1. 장바구니

**근거**: 원문 §5(개인도서 기능 목록에 장바구니 명시), Phase 2 화면 목록
**미확정**: 추천도서도 장바구니를 경유하는지 여부 (원문에 "구매하기"만 명시되어 불명확)

구성 요소:

- 도서 이미지, 제목 (표시만 — 도서 정보 자체의 상세 기획은 비담당)
- 도서가격 / 회사 지원금(−) / 직원 부담금 표시 (도서별)
- 수량 조절(1권씩), 삭제
- **주문 요약**: 총 도서가격 합계 → 회사 지원금 합계 → **직원 결제액 합계(강조 표시)**
- 지원금 적용 안내 배너 ("OO,OOO원의 B2B 기업 지원금이 적용되었습니다")
- [결제하기] 버튼

팝업/모달:
| 팝업 | 노출 조건 | 문구(안) |
|---|---|---|
| 삭제 확인 | 삭제 버튼 클릭 | "장바구니에서 삭제하시겠습니까?" |
| 월 한도 초과 안내 | 담긴 도서 합산이 월 지원한도 초과 | "월 지원금 한도를 초과했습니다" |

예외케이스:
| 케이스 | 조건 | 처리 |
|---|---|---|
| 장바구니 비어있음 | 담긴 항목 없음 | 빈 상태 화면 노출 |
| 도서 품절 | 결제 시점 재고 소진 | "일부 도서가 품절되었습니다" 안내 후 제거 유도 |
| 지원금 재계산 오류 | 가격/지원금 API 실패 | "가격 정보를 불러올 수 없습니다" + 재시도 |

### Page 2. 결제 페이지 ★ 복합결제 핵심 화면

**근거**: 원문 §7 "복합결제 시스템"

구성 요소:

```
주문 요약
├─ 도서 1: 15,000원 (추천도서) — 회사지원 15,000 / 직원부담 0
├─ 도서 2: 20,000원 (개인도서) — 회사지원 10,000 / 직원부담 10,000
└─ ────────────────────────
   총 도서가격:  35,000원
   회사 지원금: −25,000원 ✓
   ────────────────────────
   최종 결제액:  10,000원 (직원 실결제, 강조)
```

- 배송지 표시(기 등록 정보 자동입력) / 수정
- 결제 수단 선택 — **직원 결제분에 한함** (원문에 결제수단 종류 명시 안 됨, 확인 필요)
- 하나의 주문번호(Order ID)로 통합 관리됨을 명시하는 안내
- 약관 동의
- [결제하기] 버튼

결제 상태 전이:

```
결제 확인 → 결제 진행중(로딩) → 결제 성공 / 결제 실패
```

팝업/모달:
| 팝업 | 노출 조건 | 문구(안) |
|---|---|---|
| 결제 확인 | 결제하기 클릭 | "OO,OOO원을 결제하시겠습니까?" |
| 결제 진행 중 | PG 요청 중 | 로딩 스피너 |
| 결제 성공 | PG 승인 완료 + 지원금 차감 완료 | "결제가 완료되었습니다" |
| 결제 실패 | PG 승인 실패 or 지원금 차감 실패 | "결제에 실패했습니다. 사유: ~" |

예외케이스 (복합결제 특유의 리스크 지점):
| 케이스 | 조건 | 처리 |
|---|---|---|
| 결제수단 오류 | 등록된 결제수단 없음 | "등록된 결제 수단이 없습니다" + 결제수단 추가 유도 |
| 재고 소진 | 결제 확정 직전 품절 | "일부 도서의 재고가 소진되었습니다" |
| 세션 만료 | 결제 중 세션 타임아웃 | 재로그인 유도 |
| **PG 연동 오류** | PG가 복합결제(2개 결제주체) 미지원 시 발생 가능 | 재시도 안내 — **1.5절 PG 이슈 확정 전까지 발생 리스크 가장 높은 예외** |
| **회사 지원금 차감 성공 + 직원 PG결제 실패** | 두 단계 결제 중 한쪽만 성공 | **롤백 정책 필요 — 별도 확정 필요 항목(4장 참고)** |

### Page 3. 주문완료

**근거**: Phase 2 화면 목록에 명시, 상세 구성은 원문에 서술 없음(화면 문구 확인/기획 필요)

주문 시 생성되는 데이터(정산 필드와 동일):

```
Employee ID / Order ID / Book ISBN / Book Type / Format
/ List Price / Selling Price / Company Subsidy / Employee Payment
/ Order Date / Refund Status / Review Status
```

표시 요소: 주문번호, 주문일시, 도서별 결제완료 금액, 지원금 사용 내역(회사 지원금 사용액/월 남은액), 배송 정보(요약만, 배송조회 화면은 비담당), 영수증 다운로드

팝업/예외: 영수증 다운로드 완료 / 주문정보 조회실패(재시도)

### Page 4. 마이페이지 — 지원금 현황 / 구매내역 / 환불·취소 ★ 복합결제 역방향 처리

**근거**: 원문 §2 메뉴 목록("나의 구매내역", "나의 지원금"), §8(환불 시 지원금 회수 이슈)

> 마이페이지 자체(개인정보 탭 등)는 비담당 영역이며, **지원금 현황 / 구매내역 / 환불·취소 3개 탭만** 본 문서 담당.

**지원금 현황 탭**

- 이 달 사용 현황: 월 한도, 사용액, 남은액, 사용률 바
- 추천도서/개인도서 각각 신청 여부(O/X) + 사용 지원금
- 사용 상세 내역: 날짜, 도서명, 지원금, 결제액

**구매내역 탭**

- 날짜, 도서명, 유형, 가격, 지원금, 결제액 테이블 + 상세보기
- 필터(기간별/상태별), 정렬(최신순/오래된순)

**환불/취소 탭**

- 환불 가능 주문 목록 → [환불 신청] → 환불 확인 팝업 → **회사 지원금 + 직원 결제금 동시 복원 처리**
- 환불 상태(진행중/완료) 표시

팝업/모달:
| 팝업 | 문구(안) |
|---|---|
| 환불 확인 | "환불을 신청하시겠습니까?" |
| 환불 완료 | "환불이 신청되었습니다" |

예외케이스:
| 케이스 | 처리 |
|---|---|
| 환불 불가(기간 종료) | "환불 기간이 종료되었습니다" |
| 부분 환불 | "일부 도서만 환불 가능합니다" |
| 지원금 복원 실패 | 회사 지원금 복원과 직원 환불 중 한쪽만 처리된 경우 — **정합성 오류, 수동 확인 필요 플래그 처리 권장(설계 제안)** |
